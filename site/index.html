WHO IT’S FOR

A reading companion,
not an answer oracle.

ScholarLens is for students, engineers and researchers who want to discuss an AI paper in Egyptian Arabic while keeping English technical terms and original quotations accessible.

It does not replace reading the paper. A generated explanation can miss context or misread a table. The claim-checking system establishes where a retained claim came from and checks its copied support; it cannot prove that the model interpreted the science correctly.

The repository is available to run with your own bot, configuration and provider access. Core paper study uses public arXiv PDFs, SQLite and hosted generation. No local LLM weights are needed for that path.

SYSTEM DESIGN

Boundaries are part
of the product.

The diagrams describe the implementation, not a proposed future architecture. Inline SVG keeps them dependency-free.

01 / REQUEST PIPELINE

One selected version.
One bounded study graph.

The bot and study API are local. The access gate checks membership before a user’s service is resolved. The graph resolves the paper, extracts page-linked text, then teaches.

StudyService implementation
02 / CLAIM CHECK

A copied span is proof
of location, not meaning.

The writer produces claims with evidence IDs. Deterministic screens check IDs, numbers, repetition and unrequested superiority claims. A separate checker returns supporting spans; the application verifies their exact location.

Only retained paper claims reach the student, notes and job result; separately labelled background, analogies and questions follow their own checks. A closing note gives the withheld count and headings, not their text.

Claim-check decisions
What this does not guarantee

Semantic correctness, complete paper coverage, table interpretation, or equation verification. A paper-claim answer fails closed when no paper claim can be confirmed.

03 / MULTI-USER BETA

Fair access before
generation.

The beta is opt-in and owner-controlled. One-time invites create student memberships. Each student has isolated study state, daily allowances, and at most one active job.

Implemented and covered by offline tests; live Telegram acceptance remains pending.

Multi-user specification

A later claim check for a started job queues ahead of jobs that have not started; review halves share their job’s slot. These are model-call slots, not unrestricted user-session concurrency. The dollar ceiling is local accounting, not a provider invoice or billing guarantee.

04 / ROUTING + ADMISSION

Count first.
Bound each call.

The tutor serializes a strict request, checks its byte size and estimated tokens, and checks available memory. An admitted request has bounded time, output and attempts; uncertain work is not automatically replayed.

The pinned tokenizer is prepared explicitly, not fetched during generation.

Study transport

The pre-call estimate is conservative: it counts the serialized request rather than only the message text. Accepted provider usage may reach 21,000 input tokens for cost accounting. `/deep` runs an optional owner-only research worker in a separate environment; its live failure is not declared repaired.

DESIGN DECISIONS

Choose what to verify.
Say what remains uncertain.

Each decision is linked to its implementation contract and measured limitations.

Source identity

Pin the paper version and source hash.

A stored paper carries its arXiv version, PDF SHA-256, parser revision and page-block IDs. Unversioned input resolves to an explicit version; title matches require selection.

Trade-off: only allowlisted arXiv inputs are accepted. You cannot paste an arbitrary PDF URL.

paper-intake ↗
Evidence

Attach original quotations on the server.

The model chooses evidence IDs; the application supplies the excerpts. Per-claim copied spans, number checks and screens replace a single whole-lesson verdict.

Trade-off: more work per lesson, and the checker can still misunderstand the evidence. Exact support is not semantic proof.

paper-evidence ↗ · claim-check ↗
Learning

Keep dialogue separate from the paper.

Four recent turns support continuity; they never become source evidence. `/notes` retains the first lesson and exact quotes. A reading map arranges lesson sections instead of inventing causal diagrams.

Trade-off: no mastery score, automatic progress claim, or full scientific-figure generation.

paper-tutor ↗ · learning-session ↗
Research tools

Isolate `/deep` and reserve its review budget.

The optional Deep Agents worker has read-only paper tools and no host shell, general filesystem, external web search or delegated subagents. It shares the admitted job’s four-call budget.

Trade-off: a separate Python environment is required, students cannot use `/deep`, and an observed live failure remains unresolved.

study-research ↗
Multi-user

Reserve the worst case before starting work.

Invitations, per-student state, daily counts and a shared dollar ledger sit in front of a bounded model pool. Failed jobs do not consume student paper/question quotas.

Trade-off: admission is conservative and accounting is not a provider billing guarantee. The owner’s general-knowledge fallback before opening a paper is outside this ceiling.

multi-user ↗
Evaluation

Freeze the paper set and publish missing evidence.

Thirty papers span six fields: twelve development and eighteen holdout. The report distinguishes measured outcomes from unmeasured metrics and owner-delegated AI judgments from human labels.

Trade-off: the current holdout is GLM-only and incomplete. No four-model ranking, statistical-significance claim, or measured holdout faithfulness.

Measured does not
mean proven.

Frozen GLM-5.3 / DeepInfra holdout results. The current tutor uses Fireworks; these numbers are not a Fireworks benchmark.

WRITER FORMAT98.53%

67/68 calls complied with the writer schema. Gate: at least 95%.

P95 JOB LATENCY · GATE MISSED94.485s

Nearest-rank p95. The predeclared gate was at most 90 s. Median: 25.766 s.

Holdout faithfulness is unmeasured.

The single approved judging invocation stopped on its first scoring operation with provider HTTP 429. Zero of 47 answers were scored. This does not mean zero faithfulness; it means no result.

Calibration reached exactly 34/40 = 85% agreement, with Cohen’s κ = 0.6712. The 40 labels were supplied by the assistant under explicit owner delegation, not independently by humans. Calibration therefore does not establish agreement with human labels or provide holdout quality scores.
