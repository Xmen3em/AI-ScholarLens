01 The Big Idea

What this project will become — and where Phase 2 fits.

The end goal is a personal assistant that automatically pulls academic papers from arXiv, understands them, and answers your research questions with citations. That is a classic RAG pipeline: retrieve relevant documents, then let an LLM generate a grounded answer.

A real RAG system needs several moving parts running together — an API to talk to, a database to store papers, a search engine to retrieve them, a scheduler to fetch new ones, and an LLM to write answers. Phase 2 completes the first part of that data path: arXiv metadata is fetched, PDFs are downloaded and parsed in the Airflow image, and paper records are upserted idempotently into PostgreSQL. Papers outside the parser’s page limit are recorded as skips, and any failure is stored with its reason.

Built & working

The API, PostgreSQL model/repository, arXiv client, health checks, Docker stack, Airflow ingestion DAG, PDF parser service and an offline pytest suite are in place.

In progress

Phase 2 is wiring fetched arXiv papers through metadata persistence and Docling-based PDF extraction. Airflow owns the heavy PDF dependency; the API stays lightweight.

Reserved for later

OpenSearch indexing/search, embeddings, retrieval-augmented answers and evaluation are intentionally kept as replaceable Phase 3–5 boundaries.

Mental model: each phase adds one dependable slice without forcing a rewrite. PostgreSQL is the source of truth, Airflow handles scheduled ingestion, and future retrieval/LLM services can be added behind the existing repository, service and API seams.

04 How the Code Is Organised

The src/ app follows a clean layered architecture — each layer has one job and only talks to its neighbours. This separation is the whole point of the “production-grade” framing.

→

HTTP request → validated → business query → ORM object → SQL. Each arrow is a hand-off between layers.

Routers · the “what URL”

Define the live HTTP endpoints (/health, /ping, paper listing and paper lookup). They validate input and delegate to the repository.

Schemas · the contract

Pydantic models that validate incoming JSON and shape outgoing responses. They guarantee the API’s data contract independently of the database.

Repositories · the data access

PaperRepository holds all query logic — create, get_by_arxiv_id, upsert. Routers never write raw SQL; they ask the repository.

Models · the table

SQLAlchemy ORM classes. Paper maps metadata, PDF-processing output and lifecycle fields to the papers table.

db/ · the connection

A BaseDatabase interface with a PostgreSQLDatabase implementation, built by a factory. The interface means you could swap databases without touching routers.

Services · integrations

services/arxiv talks to arXiv, services/metadata_fetcher.py maps entries to papers, services/pdf_parser handles Docling, and services/ollama provides the current health check.

config & dependencies · the glue

config.py centralises settings from environment variables. dependencies.py uses FastAPI injection so handlers receive a DB session automatically.

Why bother with layers? Phase 3 can add an OpenSearch client and retrieval repository beside the existing arXiv/PDF services. The routers and schemas can evolve at the API boundary without mixing infrastructure concerns into ingestion code.

05 A Request, Start to Finish

Tracing GET /health — the one endpoint that exercises real infrastructure.

# 1. App boots — lifespan() in main.py wires up shared state
settings = get_settings()              # load config from env
database = make_database()             # factory → PostgreSQLDatabase.startup()
app.state.database = database          # test "SELECT 1", create tables if missing

# 2. Request hits the router — routers/ping.py
async def health_check(settings, database):     # deps injected by FastAPI
    with database.get_session() as session:
        session.execute(text("SELECT 1"))   # ✅ Postgres reachable?
    ollama = OllamaClient(settings)
    await ollama.health_check()                # ✅ Ollama reachable? (GET /api/version)

# 3. Response — validated against HealthResponse schema
{ "status": "ok", "version": "0.1.0",
  "services": { "database": {...}, "ollama": {...} } }

If Postgres or Ollama can’t be reached, the status degrades to "degraded" instead of crashing — exactly how a load-balancer health probe expects to behave.

The two faces of a Paper

A subtle but important pattern: the ORM model (Paper, how it’s stored) is kept separate from the Pydantic schemas (PaperCreate, PaperResponse, how it crosses the API boundary).

The repository’s upsert() ties them together: given a validated PaperCreate, it updates the row if the arxiv_id already exists, otherwise inserts a new one — the standard idempotent write you want for a data pipeline that may see the same paper twice.

Why JSON columns?

Authors, categories, sections and references are naturally structured lists. JSON keeps ingestion flexible while the schema is still evolving; OpenSearch can later receive a search-optimised projection.

11 Deep Dives

Three patterns worth understanding in detail — they’re the load-bearing ideas the rest of the course builds on.

A · How a database session reaches your handler (Dependency Injection)

You never see a router open a database connection. Instead FastAPI injects one. The trick is a chain of small functions, each declaring what it needs, resolved lazily at request time.

# dependencies.py — the chain, from app state down to a live Session

def get_database(request: Request) -> BaseDatabase:
    return request.app.state.database        # set once in main.py lifespan()

def get_db_session(database = Depends(get_database)):
    with database.get_session() as session:    # context-managed…
        yield session                         # …yielded to the handler…
                                          # …then auto-closed/rolled-back after

SessionDep = Annotated[Session, Depends(get_db_session)]   # reusable alias

# routers/papers.py — the handler just asks for the type it wants
def get_paper_details(db: SessionDep, arxiv_id: str):
    return PaperRepository(db).get_by_arxiv_id(arxiv_id)

Why yield, not return?

It makes the dependency a context manager. Code after yield runs after the response is sent — guaranteeing the session is closed even if the handler throws.

Why the Annotated alias?

SessionDep bundles the type + its provider once. Handlers stay readable (db: SessionDep) instead of repeating Depends(...) everywhere.

Why route through app.state?

The DB is built once at startup (lifespan()) and reused. Per-request you only borrow a session from the shared pool — cheap and connection-safe.

Payoff: handlers are trivially testable. In tests/ you override get_db_session with a stand-in session object — no handler code changes. That single seam is why the whole app is mockable.

B · The Repository & the idempotent upsert

All SQL lives behind PaperRepository. The interesting method is upsert — the workhorse a data pipeline needs, because Phase 2 will see the same arXiv paper more than once and must not create duplicates.

# repositories/paper.py
def upsert(self, paper_create: PaperCreate) -> Paper:
    existing = self.get_by_arxiv_id(paper_create.arxiv_id)   # unique, indexed lookup
    if existing:
        for key, value in paper_create.model_dump(exclude_unset=True).items():
            setattr(existing, key, value)                    # patch only provided fields
        return self.update(existing)                         # UPDATE
    return self.create(paper_create)                        # INSERT

“Insert or update” = idempotent

Run the same ingestion twice and the table looks identical. That property is what lets Airflow safely re-run a failed job without corrupting data.

exclude_unset=True matters

Only fields actually supplied overwrite the row — a partial update won’t blank out columns you didn’t mention. The arxiv_id index makes the existence check fast.

The repository also enforces a boundary: routers speak in schemas (PaperCreate) and receive schemas back, never raw SQLAlchemy queries. Swap PostgreSQL for something else and only this file changes.

C · Where Phase 3 search will plug in

OpenSearch is part of the Docker stack, but the application does not index or query it yet. The current seams make the next phase additive: keep PostgreSQL as the source of truth, then build a search projection from processed paper content.

12 The Ingestion Pipeline (Airflow)

The current DAG is the Phase 2 ingestion backbone: it is scheduled, retryable and split into tasks that can evolve independently.

What ships today: arxiv_paper_ingestion

A DAG (Directed Acyclic Graph) is Airflow’s unit of work — tasks plus the order in which they run. The current workflow is scheduled for weekdays at 06:00 UTC, allows two retries, and keeps ingestion steps visible in Airflow.

# airflow/dags/arxiv_paper_ingestion.py

setup_environment >> fetch_daily_papers
fetch_daily_papers >> [process_failed_pdfs,
                         create_opensearch_placeholders]
[process_failed_pdfs, create_opensearch_placeholders]
    >> generate_daily_report >> cleanup_temp_files

# schedule: 0 6 * * 1-5 · retries: 2 · max_active_runs: 1

Hostnames, not localhost

Inside the Docker network services address each other by service name — postgres, opensearch, ollama — never localhost.

0 6 * * 1-5

Automatic weekday schedule in UTC. Set a manual run from the Airflow UI when testing a change.

retries=2

Transient failures can retry after 30 minutes. Combined with the idempotent upsert, rerunning ingestion is safe.

The Phase 2 ETL path

The pipeline follows a classic ETL (Extract → Transform → Load) flow, with indexing kept as an explicit future boundary:

Extract
arXiv API
→
Transform
Docling PDF parse
→
Load
repo.upsert() → Postgres
→
Index
placeholder → Phase 3

Airflow handles scheduling, retries, logging and run history. The DAG mounts ./src into the Airflow image so task code can reuse the project’s models and services.

Why Airflow at all? You could fetch papers with a cron and a script. Airflow adds visibility, retries, backfills and dependency ordering — the operational scaffolding for an unattended pipeline. PostgreSQL remains the source of truth, while OpenSearch indexing can be added as a later task without changing the extraction contract.
